## 一、 引言：大四备考期的“刷题迷茫”

进入大四以后，求职与保研后的技术沉淀成了我每天生活的核心主线。每天下午固定抽出 2~3 个小时刷算法题、研究题解，几乎成了肌肉记忆。

但在坚持刷题两三个月后，我越来越强烈地感受到一种隐形的**“量化焦虑”**：
1. **缺乏宏观大局观**：每天点开力扣，做完 1~2 道题、看到绿色的 `Accepted` 确实有瞬间的多巴胺，但合上电脑后，我对自己的整体掌握情况依旧模糊——我到底在 Easy 题里沉溺了多久？Medium 的突破率是多少？
2. **知识盲区不可视**：力扣网页端虽然有个人主页，但信息非常分散，缺乏定制化的进度透视；
3. **从“解题者”到“造工具者”的本能**：作为计算机科班学生，面对重复性、数据统计性的需求，第一反应不应该是“手动拿 Excel 记”，而是**“能不能写个程序，让它一键把我的刷题状态拉下来、算清楚、存起来？”**

这就是 **LeetCode Tracker** 诞生的起点。

---

## 二、 核心目标：我要做一个什么样的工具？

我把这个项目的定位定义为：**轻量、无干扰、面向终端极客的算法进度量化引擎**。

它在现阶段需要满足三个最纯粹的 MVP（最小可行性产品）需求：
- **终端一键呼出**：不用打开臃肿的浏览器，命令行敲一行 `python main.py -u <username>`，秒级吐出数据；
- **核心维度可视化**：清晰呈现全站排名、提交总数、通过率，以及 Easy / Medium / Hard 三大难度的绝对数量与完成百分比；
- **本地持久化**：自动将拉取到的原始统计沉淀为本地 JSON 数据文件，为后续生成**历史成长曲线、刷题热力图和弱项雷达图**打下数据地基。

## 三、 技术架构与关键实现

整个项目采用简洁清晰的模块化架构组织：

```text
leetcode-tracker/
├── main.py              # CLI 命令行入口与流程编排
├── api/
│   └── leetcode.py      # LeetCode GraphQL 接口封装与请求容错
├── analyzer/
│   └── stats.py         # 统计数据解析与 Rich 终端表格美化渲染
├── utils/
│   └── storage.py       # 本地结构化数据持久化引擎
├── data/                # 用户刷题数据归档目录（JSON）
└── README.md
```

### 1. 深入 GraphQL API 调度
力扣前后端数据交互主要基于 GraphQL 协议。通过逆向分析其公共网络接口，我提炼出了两个核心 Query：
- `userProfilePublicProfile`：获取用户的全站排名（Ranking）与历史提交总数（Submission Progress）；
- `userProfileQuestions` / `allQuestionsCount`：拉取平台题库全集分布与该用户已 AC 的各难度题目数量。

### 2. 网络容错与双端适配
在开发过程中，我踩到了一个国内开发者普遍会遇到的坑：**力扣中国站（leetcode.cn）配置了严格的阿里云 WAF 防爬盾（alicfw）**，直接无头脚本发起 POST 请求会被拦截为 HTML 挑战页。

针对这一问题，我在 `api/leetcode.py` 中做了双层设计：
- **全球站无缝直连（默认推荐）**：支持 `--site com`，无需任何配置，秒级直出；
- **中国站 Cookie 绕过**：支持 `--site cn --cookie "..."`，允许本地开发者注入浏览器 Cookie 绕过 WAF 校验；
- **底层双通道**：优先采用异步/现代的 `httpx`，并编写了标准库 `urllib` 的零依赖回退逻辑，保障无论在何种 Python 环境下均不崩溃。

### 3. Rich 终端美化与本地持久化
通过集成 `rich` 库，利用彩色 Panel 与 Table 将原本冰冷的 JSON 字典转化为结构清晰的终端看板：

```text
┌───────────────────────────────── 用户信息 ──────────────────────────────────┐
│ 用户名: tourist                                                             │
│ 全站排名: 5000001                                                           │
│ 总提交数: 8                                                                 │
│ 通过提交数: 4                                                               │
│ 通过率: 50.0%                                                               │
└─────────────────────────────────────────────────────────────────────────────┘

           题目完成情况            
┌────────┬────────┬──────┬────────┐
│ 难度   │ 已完成 │ 总数 │ 完成率 │
├────────┼────────┼──────┼────────┤
│ Easy   │ 1      │ 975  │ 0.1%   │
│ Medium │ 2      │ 2138 │ 0.1%   │
│ Hard   │ 1      │ 987  │ 0.1%   │
└────────┴────────┴──────┴────────┘
```

数据拉取完毕后，`DataStorage` 模块会自动附带当前时间戳，把快照归档到 `data/{username}_stats.json`，完成数据采集闭环。

## 四、 开发反思与心路历程

回看这个工具的从 0 到 1，最大的收获不是写了这几百行代码，而是**研发思维的蜕变**：

1. **跳出“单纯做题”的思维定势**：
   以前刷题只是为了应付面试，容易陷入枯燥与自我怀疑；但当你为了分析刷题而写出一个工具时，你不仅加深了对网络协议、接口逆向、数据处理的理解，还真切体验到了“用代码赋能自己”的爽感。
2. **注重工程规范**：
   从第一天起就确立了清晰的模块划分、类型注解（Type Hints）与异常捕获，即使是个小工具，也要有生产级项目的架构雏形。

## 五、 后续迭代规划（Roadmap）

目前 v0.1.0 版本的 MVP 骨架已经跑通，接下来我计划在业余时间持续演进它：
- [ ] **标签维度雷达分析**：分析 Array、Dynamic Programming、Graph 各专项分类的完成率；
- [ ] **刷题热力图生成**：根据时间戳分析每天的刷题活跃度；
- [ ] **Markdown 题解骨架生成器**：根据题号自动生成标准题解模板文件；
- [ ] **轻量 Web UI / 飞书推送拓展**：支持定时汇报每周刷题增量。

把简单的事情做到极致就是能力。希望这个工具不仅能记录我的求职算法进阶之路，也能帮助到同样在刷题路上拼搏的开发者！
